# 契约匹配详解

跨程序分析的核心问题：**本程序改的这个东西，和对方程序用的是不是同一个东西？**
六类契约各有自己的对齐规则，下面逐一说清楚。

## HTTP 接口

按**规范化路径模板**匹配。

### 规范化做了什么

```text
/api/users/{id}          →  /api/users/{}      （变量名丢掉，只留占位）
/api/users/{userId}      →  /api/users/{}      （同上，两个程序变量名不同也能对上）
http://host/api/users/1  →  /api/users/1       （去掉协议与主机）
/api/users/?page=2       →  /api/users/        （去掉查询串）
/api//users/             →  /api/users         （折叠重复斜杠、去尾斜杠）
```

### 客户端写法差异的处理

客户端很少照抄模板，常见三种写法都要能对上：

| 客户端写法 | 扫描到的路径 | 匹配方式 |
|---|---|---|
| `getForObject("/api/users/42")` | `/api/users/42` | 模板变量填值 |
| `getForObject("/api/users/" + id)` | `/api/users` | 前缀匹配（拼接截断） |
| Feign 接口 `@GetMapping("/api/users/{id}")` | `/api/users/{}` | 直接相等 |

第三种情况（拼接）最容易漏。`"/api/users/" + id` 只能静态扫出字面量部分 `/api/users`，
所以匹配时还要判断"这个前缀是否正好是某个模板的前缀且剩余部分只有一个变量"。

### 支持哪些消费方写法

- Spring MVC 的 `@GetMapping` / `@PostMapping` 等（提供方）
- Feign 的 `@FeignClient`（消费方）
- `RestTemplate` / `WebClient` / `HttpClient` 里的 URL 字面量（消费方）
- OpenAPI / Swagger 规范文件里的路径

## 数据库字段

**契约的单位是 `表.字段`（`table.column`），不是表。**

只改本程序读多少列，不构成数据库契约变化——这是本节最要紧的一条规则。

### 本程序侧：哪些改动才算数据库契约

数据库变更集只收三类：

| 改动 | 例子 | 契约单位 |
|---|---|---|
| 表结构变更（DDL） | `ALTER TABLE orders ADD / DROP / MODIFY COLUMN` | 被改的那个字段 `orders.remark` |
| 写入字段集合变化 | `INSERT INTO orders(...)` 的列清单、`UPDATE orders SET ...` 的列 | 新增或消失的那个字段 |
| 实体字段映射变化 | JPA `@Column` 映射的 Java 字段新增 / 删除 / 类型变化 | 对应字段 |

`CREATE TABLE` / `DROP TABLE` 是例外：这时字段未知，退回**整表**匹配（契约单位 `orders`）。

除此之外的 SQL 改动都不产生跨程序影响：只改 `WHERE` 条件、`JOIN`、排序、分页，
语句文本确实变了，但**写入字段集合没变、表结构也没变**，对方看不出差别。

为什么变更记录要先还原字段：变更记录指向的是 `SQL_STATEMENT` 符号，不是列符号。
`insert into orders(status, ...)` 改了，`orders.status` 的契约就变了，但列符号本身没动。

```text
SQL_CHANGED  sql:.../OrderMapper.xml#updateOrder
             readsColumns:  （无）
             writesColumns: orders.status    ← 从语句元数据还原
                    ↓
             匹配对方的 db:column:orders.status
                    ↓
             OrderReader.loadOrder  （对方读这一列 → reader）
```

### 只改读取字段集合为什么不扩散

给自己多查一个字段、少查一个字段，都不算数据库契约变化。

理由很简单：**读多少列是本程序的内部行为，对方看不见。** 双方在数据库契约里共享的是
"这一列存在、类型是这样、语义是这样"，而不是"本程序读了它"。本程序多读一列，
对方的查询不会因此失败，也不会多返回一列；本程序少读一列，对方读到的数据完全一样。

```text
改前  SELECT id, status FROM orders WHERE id = ?
改后  SELECT id, status, remark FROM orders WHERE id = ?    ← 多查一列 remark
        ↓
      写入字段集合：无变化        表结构：无变化
        ↓
      不进入数据库变更集 → 对方程序不受影响（哪怕它也在读写 orders）
```

如果按表匹配，这条纯内部改动会把对方所有碰 `orders` 的模块都拉进候选队列，
和"某一列要被删掉"混在一起。真正需要通知对方的是后者，被噪声淹掉的也是后者。

### 命中条件：对方在哪算用了这个字段

字段级命中看对方程序里有没有这个字段的使用点：

| 对方的使用点 | 关系 | usage |
|---|---|---|
| 对方的 SQL 语句读这个字段 | `READS_COLUMN` | reader |
| 对方的 SQL 语句写这个字段 | `WRITES_COLUMN` | writer |
| 对方的实体字段映射这个字段 | `MAPS_COLUMN` | mapping |

命中条目记 `DB_COLUMN`，契约写 `table.column`，置信度 0.85。

**本程序改的是哪一类，决定命中对方谁：**

- **写入字段集合变化 → 只命中读方。** 本程序写不写 `orders.remark`，不影响对方怎么写它自己的值；
  但对方正在读这一列，读到的内容会变。
- **表结构变更 → 读方与写方都命中。** 列被删掉或改了类型，对方读它、写它都会出问题。
- **整表变更（`CREATE TABLE` / `DROP TABLE`）→ 退回表级匹配**，命中读写该表的代码，记 `DB_TABLE`。

实体映射（mapping）是第三种使用点：本程序改的是字段本身时（表结构变化、实体映射变化），
对方映射该字段的代码同样算命中——它读不到这一列，字段名或类型对不上就映射失败。

### 字段盲区：没读到 ≠ 没影响

字段级匹配要求能从 SQL 里解析出具体列名。两种情况解析不出来：

- 对方写的是 `SELECT *`——列清单由运行时的表结构决定，静态分析拿不到；
- 语句形态解析不了，例如动态拼接的 SQL、方言函数、非标准语法。

这类语句不再命中字段级契约，但**会被计数**，并在报告的「分析边界与盲区」里标注为**字段盲区**：

```text
字段盲区  peer-service · ReportMapper.xml:31
          SELECT * FROM orders — 列清单无法静态确定，未参与字段级匹配
```

它同时说明两件事：这条 SQL 确实碰了本程序改的表，但工具判断不了它碰没碰那个字段。
把盲区读成"没影响"是最容易犯的错，所以它出现在盲区清单里，而不是被静默丢掉。

### 一张对照表

| 本程序的改动 | 是否扩散 | 命中对方谁 |
|---|---|---|
| 多查 / 少查一个字段 | 否 | —— |
| 只改 `WHERE` / `JOIN` / 排序 | 否 | —— |
| 写入字段集合新增或消失 | 是 | 读该字段的代码（reader） |
| 实体字段映射新增 / 删除 / 类型变化 | 是 | 读方、写方、映射方 |
| DDL 加字段 | 是 | 读方与写方 |
| DDL 删字段 / 改字段类型 | 是 | 读方与写方 |
| `CREATE TABLE` / `DROP TABLE` | 是（表级） | 读写该表的代码 |

## 配置项

按 key 匹配，并且**向上追溯父级前缀**：

```text
本程序改动 config:app.limit
  ↓ 候选
config:app.limit    ← 精确匹配
config:app          ← 父级前缀
  ↓
对方绑定 @ConfigurationProperties(prefix = "app") 的类   ← 命中
```

反过来也成立：改 `app` 前缀下的任意 key，会影响绑定该前缀的类。

`@Value` 注解在**字段上**和**方法参数上**都会被扫描。字段注入是最常见的写法，
只扫方法会漏掉大量消费方。

## Maven 依赖

如果对方 pom.xml 声明了对本程序某个模块 artifactId 的依赖，就是编译期契约。

```text
本程序模块 artifactId: common
  ↓
对方 pom.xml 里有 <dependency><artifactId>common</artifactId>
  ↓
编译期契约命中
```

这类命中只报告"存在依赖关系"，不产生具体影响条目——因为依赖本身不是某个符号的使用点，
需要靠其他契约（类型引用、方法调用）才能定位到代码。

## 消息主题

按**规范化标识**匹配，覆盖三种中间件：

| 中间件 | 契约标识 |
|---|---|
| Kafka | Topic 名 |
| RabbitMQ | Exchange + Queue + Routing Key |
| RocketMQ | Topic + Tag |

## 消息 Schema

同一中间件下，消息体的**结构指纹**一致即视为同一契约：

- 字段名、字段类型、必填性
- 枚举取值集合
- JSON DTO / Avro / Protobuf 文件

Schema 变化特别隐蔽：字段类型从 `int` 改 `long`，生产者能跑，消费者也能跑，
但反序列化可能丢精度。这类变更需要靠契约匹配才能发现。

## 匹配失败怎么办

匹配不到不代表没影响，只代表**静态分析找不到连接点**。报告里会区分两种情形：

| 情形 | 报告表现 |
|---|---|
| 契约没被改动 | 不出现（共享接口没变，本来就不该报） |
| 契约改了但对方没使用点 | 显示"没有发现相关契约使用点" |
| 对方程序读取失败 | 该 peer 条目标注原因，其他 peer 不受影响 |
