# 故障排查

## 分析结果为空

按顺序检查：

### 1. 是否选了其他程序？

```text
POST /api/analyses {"sourceId": 1, "peerSourceIds": []}
→ 400 {"error":"请至少选择一个要扫描的其他程序"}
```

只选被改动的程序本身不算——自身影响不在扫描范围内。

### 2. 本次是否真的有契约变更？

如果只改了内部实现（变量重命名、提取私有方法），没有触及任何契约，
那么对其他程序确实没有影响。看报告里的「变更清单」确认识别到了什么。

### 3. 对方是否真的在用这个契约？

看该 peer 条目的 `matches`：

```json
{ "matches": [], "impacts": [], "note": null }
```

`matches` 为空说明没有找到使用点。常见原因：

- 对方调用的是动态拼接的 URL（`baseUrl + path`），静态扫不到
- 对方通过反射或脚本调用，不是 Java 代码
- 表名 / 字段名 / 配置 key 拼写不同（大小写、下划线 vs 驼峰）
- 对方用 `SELECT *` 查这张表：列清单静态确定不了，不会命中字段级契约，
  而是进入报告的**字段盲区**清单。这类情形要在盲区里找，不要看 `matches`。
- 两侧声明的数据库不同（JDBC URL 解析出的库名不同）：候选会被排除，报告会给出「因数据库不同被排除」计数
- 改动属于兼容变更（加列、类型放宽）：不扩散，报告会给出「因类型兼容被排除」计数

## 对方程序读取失败

```json
{ "peerSourceName": "order-service", "note": "无法读取该程序：目录不存在：/path" }
```

只有该条目失败，其他 peer 不受影响。检查位置是否可达、Git 凭据是否配置。

## 定时扫描不触发

### 确认配置生效

```bash
curl http://127.0.0.1:9996/api/schedule | python3 -m json.tool
```

`enabled` 必须是 `true`。注意 cron 是**六段式**（秒 分 时 日 月 周），
五段式会被解析成错误时间。

### 确认程序被正确跳过还是漏掉了

看 `last.details`：

| outcome | reason | 含义 |
|---|---|---|
| `SCANNED` | 有新提交 abc123 → def456 | 正常 |
| `SKIPPED` | 没有新提交 | 正常 |
| `SKIPPED` | 已有分析在进行中 | 上一次还没跑完 |
| `SKIPPED` | 位置不可访问：/path | 目录被删或移动 |
| `SKIPPED` | 没有其他程序可比较 | 只注册了一个程序 |
| `FAILED` | ... | 见对应错误 |

### 手动触发验证

```bash
curl -X POST http://127.0.0.1:9996/api/schedule/run
# 然后轮询
watch -n5 'curl -s http://127.0.0.1:9996/api/schedule | python3 -c "import json,sys; d=json.load(sys.stdin); print(d[\"running\"], d[\"last\"][\"status\"])"'
```

## 接口很慢或超时

### /api/analyses 慢

历史报告可能有几 MB（完整 JSON）。列表查询**不应该**读取报告内容。
如果这一项变慢，检查 `Store.analyses()` 是否用了 `SELECT *`——那会把所有 report_json 都读出来。

### 扫描一直 RUNNING

完整扫描要 fetch 远程仓库（每个可能几十秒）。4 个程序 2~3 分钟是正常的。
超过 10 分钟仍然 RUNNING，可能是网络卡住：

```bash
# 看是否卡在 fetch
tail -50 code-association.log | grep -i fetch
```

强制恢复：重启服务，启动时会把孤儿任务标记为失败。

## 服务无响应但进程还在

典型症状：`/api/health` 正常，但静态资源请求挂住，日志里有
`ClassNotFoundException: ch.qos.logback...`。

原因：运行中的 JVM 打开了 `target/code-association.jar`，而这个 jar 被
`mvn package` 就地覆盖了。重启即可恢复。

**预防**：不要对着正在运行的实例执行 `mvn package`。构建到别的目录，或先停服务。

## 端口被占用

```bash
lsof -nP -iTCP:9996 -sTCP:LISTEN    # Linux 无 lsof 时：ss -ltnp | grep 9996
./stop.sh        # 会等到端口真正释放才退出
./start.sh
```

Windows：

```bat
netstat -ano | findstr :9996
stop.bat         :: 按 pid 文件 → 端口 → 命令行逐级兜底
start.bat
```

`stop.sh` / `stop.ps1` 都会等到**端口真正释放**才退出（最多 10 秒），避免紧接着启动撞端口。

两者的"停"并不相同：`stop.sh` 发 `SIGTERM`，JVM 会跑 shutdown hook；Windows 没有等价的信号，
`stop.ps1` 只能结束进程（`TerminateProcess`），JVM 的 shutdown hook 不会执行。
这对本服务**几乎没有**影响：它没有注册任何 shutdown hook，SQLite 用 rollback journal 崩溃安全，
被中断的分析下次启动时会被标记为失败。

两处例外值得知道：

- `{data-dir}/repos` 下的 JGit 克隆缓存没有自愈能力。克隆 / 拉取中途被杀可能留下 `*.lock`
  或半个对象库，下次分析会失败——删掉对应目录让它重新克隆即可。
- **看到「已停止」才是真的停了**。结束失败时脚本会打印「无法结束进程」并**以退出码 1 结束**，
  所以 `stop.bat && start.bat` 不会在服务还活着的时候继续启动。

## 启停脚本报「缺少命令」或行为异常

`start.sh` / `stop.sh` 不硬依赖单一工具，但不同机器上走的分支不同：

| 症状 | 原因 | 处理 |
|---|---|---|
| 提示「没有 setsid 也没有 python3，退化为 nohup」 | Linux 极简镜像 / macOS 无 python3 | 关掉终端可能带走服务；装 `python3` 或 `util-linux`（提供 setsid）可恢复 |
| 找不到监听 PID（PID 显示 `?`） | 没有 `lsof` / `ss` / `netstat -tlnp` | 装任意一个即可；不影响启动本身，只影响 PID 文件准确性 |
| 健康检查一直超时但进程活着 | 没有 `curl`，走了 `/dev/tcp` 探测 | 装 `curl`；或直接用浏览器打开 `http://127.0.0.1:9996/api/health` |
| Windows 脚本中文乱码 / 语法报错 | `.ps1` 被存成了无 BOM 的 UTF-8 | 用发布包里的原文件，不要用编辑器另存；`release.sh` 已做 BOM 校验 |
| `stop.bat` 提示「进程无窗口，无法发送关闭信号」 | 旧版 `stop.ps1` 把 `CloseMainWindow()` 当主路径，而 java 是控制台进程，永远拿不到主窗口 | **升级即可**：当前版本停止那一步只输出「已停止 (PID N)」，并省掉白等的 3 秒。旧包没有 `-Verbose` 输出，只能忽略这条提示——它不影响停止结果 |
| `stop.bat` 说「已停止」但端口仍被占用 | 旧版没复核结束结果；或进程以管理员启动、当前 shell 权限不足 | 用**管理员**身份重开终端再执行 `stop.bat`；`netstat -ano` 查到 PID 后用任务管理器结束 |

## 深色模式下图表颜色不对

依赖图（Cytoscape）把颜色烘进画布，无法继承 CSS 变量。
主题切换时 `app.js` 会读取令牌计算值并重建图实例。如果颜色没更新，硬刷新一次页面。

## AI 审核失败

AI 审核是可选层，它的失败不影响静态分析结论与 `--fail-on` 退出码。以下三种最常见。

### 401 / 403

**现象**：AI 卡片显示 `HTTP 401: ...` 或 `HTTP 403: ...`；「测试连接」返回 `ok=false`。

**原因**：

| 状态码 | 常见原因 |
|---|---|
| 401 | Key 未填、已失效、被截断，或复制时带上了多余的空格与引号 |
| 403 | Key 有效但无该模型的权限；组织策略或区域限制；余额 / 额度耗尽时部分服务也返回 403 |

**处理**：

1. 在设置页「API Key」输入框重新粘贴一次完整 Key 并保存（输入框本身是空的，占位符里的
   「已保存 sk-a…3f9c」才是掩码；留空保存表示不修改）；
2. 点「测试连接」，看返回的 `endpoint` 是不是预期的地址；
3. 仍失败则用同一把 Key 直接 curl 一次，确认不是服务端账号问题：

```bash
curl -sS https://api.deepseek.com/v1/chat/completions \
  -H "Authorization: Bearer $AI_API_KEY" -H 'Content-Type: application/json' \
  -d '{"model":"deepseek-chat","messages":[{"role":"user","content":"ping"}],"max_tokens":8}'
```

日志里不会出现 Key，所以排查时不要指望从日志里读到它——能读到的只有 `enabled` / `baseUrl` /
`model` / `maxImpacts`。

### 超时

**现象**：AI 卡片显示超时原因；「测试连接」返回 `ok=false` 且 `message` 含「连接超时」。

**原因**：

- 端点不可达（内网服务没起、代理没配、DNS 解析不了）；
- 模型本身慢：本地 Ollama 首次加载模型、大模型冷启动、长上下文都会超过默认 60 秒；
- 影响条目太多导致提示词过长，`max-impacts` 偏大时更容易撞上。

**处理**：

| 情况 | 处理 |
|---|---|
| 本地模型冷启动慢 | 先在终端跑一次让模型驻留；或在设置页把「请求超时（秒）」调大（上限 300，默认 60） |
| 网络不可达 | 确认容器 / 服务能访问该端点；容器里的 `localhost` / `127.0.0.1` 指容器自己，Ollama 在宿主机时要换地址 |
| 提示词太长 | 调小「每条分析最多送审影响」（默认 12） |

超时只影响这一次解释，报告其它部分照常可用，可以稍后从分析页重试。

### 返回空内容

**现象**：AI 卡片显示「AI 评审说明生成失败」，原因是「模型返回了空内容」或「无法解析响应：…」；
「测试连接」却返回 `ok=true`。

**原因**：

- 端点返回的 `choices` 为空数组（模型拒答、触发内容策略、被网关改写）；
- `choices[0].message.content` 为 `null`（部分兼容实现把正文放在 `reasoning_content`
  等非标准字段，标准字段留空）；
- 推理型模型把 `max_tokens` 全花在推理上，正文被截断成空。

**处理**：

1. 用「测试连接」确认端点确实是 OpenAI 兼容的 `/chat/completions`——只实现了部分字段的
   网关最容易出现这种"能连通但拿不到正文"；
2. 换一个模型名再试（推理型模型与 `deepseek-chat` 这类对话模型的输出形态不同）；
3. 调小「每条分析最多送审影响」后重新生成，缩短提示词；
4. 直接 curl 同一端点，看原始响应里 `choices` 与 `message.content` 到底是什么。

空内容被当成**失败**而不是成功：报告里记的是 `generated: false` 加原因，界面上是可重试的红色提示，
不会存下一张没有正文的卡片。「测试连接」只验证连通性（要求模型回 `pong`），所以它通过并不代表
完整提示词能拿到正文——两者用的不是同一个请求。

## 还想定位更细

```bash
# 分析进度（阶段 + 百分比 + 当前文件）
curl -s 'http://127.0.0.1:9996/api/analyses?limit=1' | python3 -m json.tool | grep -A3 progress

# 完整报告
curl -s 'http://127.0.0.1:9996/api/analyses/42/report' | python3 -m json.tool | head -80
```

报告里的 `blindSpots` 列出所有解析失败的调用点——"为什么没找到影响"的答案常在这里。
