# 数据库影响判断：如何减少误报

跨程序数据库影响的判定目标不是「找出 A 和 B 是否访问同一张表」，而是：

> **A 的这次改动，是否改变了 B 能观察到的数据库契约或数据行为？**

「同名表」只是候选，不是结论。本文说明判定层在候选之后还要经过哪些准入条件，以及每条规则为什么能减少误报、又会在哪里留下盲区。

## 1. 四个准入条件

一条数据库候选要成为跨程序影响，必须同时满足：

| 条件 | 问题 | 不满足时 |
|---|---|---|
| **同一数据库对象** | 两个程序真的能看见同一张表吗？ | 排除，并计数 |
| **变更可被观察** | 对方的读写方式能感知这次改动吗？ | 不命中；必要时记盲区 |
| **契约不兼容** | 改动会让对方已有的值、绑定或映射失效吗？ | 兼容变更只计数，不报告 |
| **解析足够确定** | 列名、类型、可空性是否真的解析出来了？ | 降低置信度或记盲区，不猜测 |

这四条分别对应下面四节。核心原则是：**发现依赖不等于证明缺陷；无法证明时，宁可标成盲区，也不要伪装成命中或干净结果。**

## 2. 同一数据库对象：表名不是身份

`orders`、`user`、`order_item` 这类表名几乎每个库都有。只按 `table.column` 匹配，会把无关程序拉进审核队列。

系统从两个来源读取数据库身份：

1. **配置中的 JDBC URL**：`spring.datasource.url`、`spring.datasource.*.url`、`spring.datasource.hikari.jdbc-url` 等，解析出数据库名。
2. **SQL 中的显式 schema**：`order_db.orders` 的 `order_db`，或 DDL 中的 `schema.table`。

判定规则：

- 两侧都已知、且**同一层级**（都是数据库名，或都是 schema 名）且不同 → 排除，计入「因数据库不同被排除的候选」。
- 一侧已知、另一侧未知 → **保留匹配，但置信度降低**。读不到 URL 不是「不同库」的证据。
- 两侧都是未知 → 保留匹配，置信度降低。
- 数据库名与 schema 名属于不同层级，不直接比较；否则「URL 指向 `order_db`」与「SQL 写 `order.orders`」会被误判为不同库。

为什么只比较数据库名、不比较 host：同一套 schema 在开发、测试、生产通常通过不同 host 访问；host 不同不代表库不同。

嵌入式数据库（H2 mem、HSQLDB、Derby、SQLite）不参与身份比较：它们是进程内数据库，两个程序都把库命名为 `testdb` 并不共享任何数据。

## 3. 变更可被观察：不是所有 DDL 都会影响对方

数据库契约的单位是 `table.column`，但不同 DDL 对使用方的影响方式不同：

| 本程序改动 | 对方读方 | 对方写方 | 对方实体映射 | 判定 |
|---|---|---|---|---|
| `DROP COLUMN` | 命中 | 命中 | 命中 | 列不存在，读写与映射都会失败 |
| `RENAME COLUMN` | 命中（旧列） | 命中（旧列） | 命中（旧列） | 旧列名消失；新列名不可能已是依赖 |
| `MODIFY` 收窄 / 类型不兼容 | 命中 | 命中 | 命中 | 值可能截断、精度丢失或隐式转换 |
| `MODIFY` 放宽 / 兼容 | 不命中 | 不命中 | 不命中 | 已有值与绑定仍然有效，只计数 |
| `MODIFY` 可空性收窄（NULL → NOT NULL） | 不命中 | 命中 | 不命中 | 读方仍读到相同值；写方可能被拒绝 |
| `MODIFY` 默认值变化 | 不命中 | 不命中 | 不命中 | 只影响省略该列的写入，进入盲区 |
| `ADD COLUMN` | 不命中 | 不命中 | 不命中 | 按列名读写的代码看不见新列 |
| `CREATE TABLE` | 不命中 | 不命中 | 不命中 | 新表不可能已经是对方的依赖 |
| `DROP TABLE` | 命中 | 命中 | 命中 | 整表消失，退回表级契约 |
| 删除迁移脚本 | 不命中 | 不命中 | 不命中 | 已执行的 migration 不会因为删文件而回滚 |
| 写入字段集合变化 | 命中 | 不命中 | 不命中 | 本程序开始/停止写某列，只有读方能观察到值变化 |
| 无列名的整表写入 | 命中 | 不命中 | 不命中 | 行级写入变化，但仅限解析不出列名时 |
| 实体字段新增 | 不命中 | 不命中 | 不命中 | 加映射是程序内部行为 |
| 实体字段删除 / Java 类型变化 | 不命中 | 不命中 | 低置信度提示 | 字段映射不是数据库 schema |

### 新增列为什么不再命中读方

```text
A: ALTER TABLE orders ADD COLUMN remark VARCHAR(64);
B: SELECT id, status FROM orders WHERE id = ?
```

B 的列清单是写死的，新列不会让 B 的 SQL 失败，也不会改变 B 读到的 `id/status`。真正可能受影响的是：

- 对方写 `SELECT *`：列清单由运行时 schema 决定；
- 对方写 `INSERT INTO orders VALUES (...)`：没有列清单，新增列可能改变插入语义；
- 新增列是 `NOT NULL` 且没有默认值：无列名 INSERT 可能被拒绝。

这些情况无法用「对方是否读这一列」判断，因此进入**字段盲区**计数，而不是把每个读方都报成受影响。

### 兼容变更为什么只计数

```text
VARCHAR(32) → VARCHAR(64)     放宽，已有值全部可表示
INT → BIGINT                  放宽，已有值全部可表示
DECIMAL(10,2) → DECIMAL(12,2) 精度增加
DATE → DATETIME               时间信息增加
可空 → NOT NULL               收窄（写方可能失败）
```

类型兼容规则集中在 `ColumnTypeCompatibility`。只有收窄、类型族变化或无法判断时才命中；放宽只计入「兼容变更」计数，报告会说明有多少条候选因此没有扩散。

## 4. 解析足够确定：动态 SQL 不能降级成表级契约

字段级匹配依赖从 SQL 中解析出列名。以下情况解析结果只是**下界**，不是事实：

- MyBatis `<if>` / `<choose>` / `<foreach>` / `<include>`；
- 占位符拼接（如 MyBatis 的美元占位符）；
- `SELECT *`；
- `INSERT ... SELECT` 的目标列清单缺失；
- 存储过程、视图、触发器、运行时动态表名。

处理方式：

- **本程序侧**：解析不完整时，不把「没解析出写入列」当成「写入列集合变了」，也不退回整表契约。
- **对方侧**：碰到变更表但没有明确列名的语句，计入「字段盲区」，在报告中列出文件与行号。
- **盲区口径**：只有「读写列都没解析出来」或「语句被标记为不完整」才算盲区；一条已经作为 writer 命中的纯写语句不会重复计入盲区。

此外，SQL 符号按文件与行号标识，语句从一个 mapper 移到另一个会同时产生「删除」和「新增」。变更检测会按规范化文本配对这两条记录并取消；文件搬家不应被读成写入字段集合变化。

`SELECT *` 不是「没有使用这个字段」，而是「无法静态判断使用了哪些字段」。把盲区读成「没影响」是最容易犯的错误，所以它出现在报告里，而不是被静默丢弃。

## 5. 实体映射与数据库 schema 解耦

JPA 实体字段变化过去被当作 schema 变化，导致每次实体重构都命中对方读写方。现在：

- `FIELD_ADDED`：不产生数据库 delta；
- `FIELD_REMOVED` / `FIELD_TYPE_CHANGED`：只对**同样映射该列**的对方代码产生低置信度 `mapping` 提示，不命中 SQL 读写方；
- 只有显式 `@Column(name=...)` / `@JoinColumn(name=...)` 才作为映射证据；隐式 camelToSnake 的置信度更低；
- `@Transient`、`static`、集合类型（`List` / `Set` / `Map` / 数组）不建列映射；
- `userID` → `user_id`、`URLPath` → `url_path`，按 Hibernate 的边界规则转换，而不是每个大写字母都插下划线。

真正的 schema 变化仍由 DDL / 迁移脚本捕获，与实体映射分开。

## 6. 报告如何保持透明

减少误报不能变成「悄悄不报」。报告会保留：

- **因数据库不同被排除的候选数**，并给出一句人工复核建议；
- **因类型兼容被排除的候选数**，按变更计（同一处改动对比多个程序不会重复累加）；
- **对对方不可观察的变更数**：加列、建表、删除迁移脚本——不扩散，但计数并给出示例；
- **字段盲区**：碰到变更表、但无法解析列名的对方语句；
- **未知项**：动态 SQL、无法解析的 DDL、存储过程等。

这些计数不参与风险分，但它们决定了「没有发现影响」到底有多可信。

## 7. 仍然没有解决的问题

| 问题 | 现状 | 下一步 |
|---|---|---|
| 写入列集合不变、值语义变了 | 不产生 delta | 比较 SET/INSERT 赋值表达式；只命中按该列过滤的对方代码 |
| 事务边界、提交时机、锁顺序 | 不分析 | 解析 `@Transactional`、`FOR UPDATE`、更新顺序，结合并发测试 |
| 视图 / 触发器 / 存储过程 / 外键级联 | 不建依赖图 | 采集数据库元数据，沿对象依赖传播 |
| 真实数据分布 | 不读取 | 在隔离测试库执行迁移并校验数据 |
| 运行时实际 SQL | 不采集 | MyBatis 插件 / JDBC 代理 / OpenTelemetry 补全 |
| 多版本共存 | 静态契约兼容 | 扩展—迁移—收缩，校验新 A 与旧 B |
| 同一程序多数据源 / 多 schema 同名表 | 快照键只有 table.column，可能互相覆盖 | 按数据源 / 模块隔离键 |
| 一条 ALTER 里的多个动作 | 只处理第一个动作 | 按顶层逗号拆分动作 |

这些是已知边界，不是「已经支持」。报告中的「未发现影响」只表示在静态契约层没有找到不兼容证据。

## 8. 一张判定流程图

```text
A 的代码 / SQL / DDL 变更
        │
        ▼
还原数据库 delta：表.列 + 操作类型 + 旧/新类型 + 可空性
        │
        ├─ 删除迁移脚本 / 新增表 / 加列 / 兼容放宽 ──→ 不扩散（计数）
        │
        ▼
查对方使用点：READS_COLUMN / WRITES_COLUMN / MAPS_COLUMN
        │
        ├─ 数据库身份不同 ──→ 排除（计数）
        │
        ├─ 操作类型不接受该使用点 ──→ 不命中
        │
        ▼
命中：进入对方调用图传播，计算风险与置信度
        │
        ▼
未命中但表相同且列名不可解析 ──→ 字段盲区（人工确认）
```
